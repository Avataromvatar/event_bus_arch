# Post-4.1 hardening, probe and migration plan

- Date: 2026-11-24
- Scope: core `event_bus_arch`, `event_bus_arch_transport`, package tests, tooling and docs
- Source: follow-up review after 4.1.0; the `initTimeout` zombie was reproduced with a controlled
  slow `onInit`
- Status: partially implemented — 4.1.1 scope done; migration and API design pending

## 1. Findings

### F-01 (P0) `initTimeout` leaves a live worker

The timeout callback in `EventBusIsolate._init` only calls `_completeInitError`
(`lib/src/event_bus_isolate.dart:752-757`). It does not invalidate the generation, close the
`ReceivePort`, kill the isolate, clear `_link.sendPort`, or set `_ready = false`,
`_workerGone = true`.

Consequences:

- a hung `onInit` leaves an isolate and a `ReceivePort` alive for the whole process;
- a slow `onInit` can send `_IsolateReady` after `waitInit` already failed. The receive callback
  sets `_ready = true`, so `isInit` becomes true, `ping` answers, and `fire`/`request` start
  working while the caller has observed an initialization error;
- a late message can also mutate remote interest after the caller has treated the bridge as
  failed.

Required invariant: after a timeout, the initialization generation is aborted, the worker and its
port are gone, and no late message from that worker can make the bridge usable. `waitInit` then
completes with `EventBusException`.

### F-02 (P1) `RequestProbe` has no transport capability

`FireProbe` reports `transportPublishes`, but `RequestProbe` reports only local handlers and
isolate interest (`lib/src/event_probe.dart:47-80`). A `TransportEventBus` with a codec that can
both encode and decode has no local handler, so `probeRequest(...).hasHandler` is false even
though `request` will go to the broker.

The probe is documented as returning local/remote/transport statistics, so this is a reporting
gap, not only a naming issue.

### F-03 (P1) Release metadata and dependencies are stale

- `pubspec.yaml:2` still promises `FSM` in the core package, although patterns moved to
  `event_bus_arch_patterns`.
- `intl` and `async` are direct dependencies but have no production or test imports;
  `async` is only present in a commented-out import.
- The 4.1.0 CHANGELOG entry says package versions are “unpublished” instead of stating the
  release facts.
- Package CHANGELOGs and install snippets must stay aligned with the current core constraint (`^4.1.1` after the 4.1.1 release).

### F-04 (P1) Migration path is incomplete

- There is no user-facing 3.x → 4.x migration guide.
- `tool/migrate_3_to_4.dart` rewrites only `handlers.setHandler` → `subscribe`; it reports a few
  handler removals but does not inspect `paths:`, `separator:`, `Topic`/`TopicPattern`,
  `subscribeEvents`, `currentData`, `have*` or `removeTopic`.
- The test-only `test/legacy_compat.dart` facade is still used by 30 files (29 test files and
  one NATS benchmark). A fresh audit finds 233 test blocks containing legacy calls (652
  `*Legacy` calls); the earlier estimate of 201 is below the current count, so the target metric
  is “zero legacy calls”, not a fixed count.
- The production API is E-only, but tests still exercise the old type-prefixed path shape; this
  hides regressions in the new address API and makes examples misleading.

### F-05 (P2) Typed request and middleware are unresolved API gaps

- `EventBus.request` returns `Future<dynamic>`; the response type is not part of the key or the
  method contract. Typed handlers exist only at the handler boundary.
- There is no middleware or request pipeline (retry, logging, auth, tracing, metrics hooks) at
  the bus level. Transport observability is not a general-purpose pipeline.
- Both are API design decisions, not mechanical fixes. They must not be smuggled into a patch
  release.

## 2. Decisions and recommendations

1. **Timeout aborts initialization, in this order:** invalidate the generation and mark the
   bridge not ready, fail pending link work, close the receive port, kill the isolate, report an
   `isolateInit` error, and only then complete `waitInit` with an error. Reuse the same abort path
   for a worker `onInit` error so both paths have identical cleanup.
2. **`RequestProbe` gets a transport flag.** Add `bool transportRequests` (default `false`) and
   `bool get canRequest => hasHandler || transportRequests`. Keep `hasHandler` meaning “a local
   or remote handler is known”; document that `canRequest` is the routing question. The transport
   hook returns true only when the keyed codec has both `encode` and `decode`, matching the actual
   `TransportEventBus.request` precondition. The flag describes capability, not a live connection
   or a broker subscriber, by the same rule as `FireProbe.transportPublishes`.
3. **Migration is explicit.** A 3.x type-prefixed topic (`int.sensor.temp`) and a 4.x application
   address (`sensor.temp`) are different routing identities. The migration tool may suggest a
   path-derived address, but the user must choose the final address and version. Automatic
   rewriting of `paths:` is opt-in and collision-aware; the default is a report.
4. **Legacy tests are migrated before breaking API work.** This avoids rewriting the same tests
   twice and proves that the new API covers the old scenarios. The facade is deleted only after
   the last legacy call is gone.
5. **Typed request and middleware are design tasks.** Prefer an additive typed response API if it
   is source-compatible; otherwise the design belongs to 5.0. Middleware is designed separately
   from typed responses so the two changes can be accepted or rejected independently.
6. **Release mapping.** If 4.1.0 is still unpublished, fold F-01/F-02/F-03 into 4.1.0. Otherwise
   ship them as 4.1.1. Migration guide/tooling and test migration can ship in 4.2.0. Typed
   request/middleware are design-only until a decision record is accepted.

## 4. Work packages

### WP-1 — Initialization abort (REL-01, REL-02)

- Extract a private `_abortInit` helper in `event_bus_isolate.dart`:
  - guard `generation` and `_completerInit.isCompleted`;
  - increment `_generation` so a spawn that has not returned is killed at its completion check
    and every late message is ignored;
  - set `_workerGone = true`, `_ready = false`;
  - call `_link.failAllPending` (or an equivalent link reset) and clear `sendPort`;
  - close and null `_receivePort`;
  - kill and null `_isolate`;
  - report `EventBusErrorKind.isolateInit` once;
  - complete `waitInit` with `EventBusException` only after cleanup.
- Use the helper for `_IsolateInitError` as well, preserving its original error and stack trace.
- Keep `restart()` usable after an abort: it replaces `_link`, resets `_workerGone`, and creates a
  new generation.
- Tests:
  - worker sleeps longer than `initTimeout`, then would send ready: `waitInit` fails, `isInit`
    stays false after the old sleep completes, `ping` is false, `fire`/`request` throw
    `StateError`, and no late interest appears;
  - the timeout reports one `isolateInit` error and does not report `isolateDeath`;
  - `restart()` after a timed-out worker reaches ready with a fast second init;
  - existing `initTimeout: null` and exit-before-ready tests stay green.
- Do not use a timing assertion that only checks the error; the zombie regression is the state
  after the worker's delayed ready would have arrived.

### WP-2 — Request probe transport capability (PROBE-01, PROBE-02)

- Add `transportRequests` to `RequestProbe` with a default of `false` to keep manual
  construction source-compatible.
- Add `bool get canRequest => hasHandler || transportRequests`.
- Add a core hook `probeRequestsKey<T>(EventKey<T> key) => false`; override it in
  `TransportEventBus` to require `codec.encode != null && codec.decode != null`.
- Keep `hasHandler` local/remote-only and document the distinction; `isBusy` remains about local
  handler capacity.
- Tests: core false; transport with both halves true; encode-only false; no codec false; local
  handler plus transport true; disconnected connection still reports the capability and the
  documentation states why.
- Update `doc/02-event-bus.md`, `doc/06-api-reference.md`, transport README and the CHANGELOG.

### WP-3 — Metadata and dependency hygiene (META-01)

- Replace the root pubspec description with a routing/eventing description that does not promise
  FSM or patterns in core.
- Remove `intl` and `async` from `pubspec.yaml`; run `dart pub get`, the full analyzer and all
  suites. Keep any dependency that is proven to be used.
- Rewrite the 4.1.0 “unpublished” sentence as a factual version/dependency statement.
- Check the package CHANGELOGs and install snippets remain at `event_bus_arch: ^4.1.0`.

### WP-4 — Migration guide and tool (MIG-01, MIG-02)

Guide contents:

- version/wire compatibility warning and the fact that there is no 3.x adapter;
- address choice: stable, versioned, application-owned, no `Type.toString()` token;
- old → new mapping for `fire`, `request`, `listen`, `subscribe`, `subscribeEvents`,
  `currentData`, `have*`, `removeTopic`, `Topic`/`TopicPattern`, `paths`/`separator`;
- handler migration (`handlers.setHandler` → `subscribe(handler:)`, store the subscription for
  cancellation);
- transport migration (`serializers`/`deserializers`/`typeTags` → `EventCodecRegistry`,
  `TransportEventBus.keys`, NATS/MQTT `.keys`);
- patterns migration (`FSM`/`Scope`/`Command` from `event_bus_arch_patterns`);
- a worked before/after example and a checklist;
- tool usage: dry run, review, opt-in rewrite, collision warnings, manual steps.

Tool requirements:

- extend `MigrationReport` with counts for path calls, separator calls, `Topic`/`TopicPattern`,
  `subscribeEvents`, `removeTopic` and legacy transport registries;
- report file and line (the current summary is not enough for a 30-file migration);
- default remains a report; `--write` applies only rewrites that are safe and reviewed;
- an opt-in path rewrite (for example `--rewrite-paths=<prefix>`) may turn a literal path list into
  `EventKey<T>('<prefix>.<path>')`; it must report cross-type collisions and require the user to
  choose the final address;
- multi-line or computed path lists are reported, not rewritten;
- fixtures cover `fire`, `request`, `listen`, `subscribeEvents`, `currentData`, `have*`,
  `removeTopic`, a clean file and a collision;
- tests extend `test/migration_script_test.dart`.

### WP-6 — Typed request and middleware design (API-01, API-02)

Do not implement before the decisions are accepted.

Typed request options:

- A. `Future<R> request<T, R>(...)` plus `Handler<T, R>`; verify Dart inference for existing
  `await bus.request(key, data)` call sites; if it stays source-compatible, this is the preferred
  additive change.
- B. A `RequestKey<T, R>`/RPC binding that carries request and response types; strongest typing,
  larger break and transport/isolate impact.
- C. Keep `dynamic` and add typed extension methods; least break, weakest contract.

Middleware design:

- local interceptor chain around `fire`/`request`, ordering and short-circuit rules;
- error, timeout and `CancelToken` interaction;
- metrics/observability hooks and redaction;
- whether middleware is local-only or crosses isolate/transport boundaries (default: local only);
- one accepted ADR with examples and rejected alternatives before implementation.

## 7. Definition of done

- Every task in the register is either accepted with tests or explicitly deferred with a decision.
- The timeout defect has a test that fails on the current code and passes after the abort cleanup.
- `RequestProbe` reports transport request capability without changing `hasHandler` semantics.
- Pubspec metadata is accurate and unused direct dependencies are gone.
- The migration guide exists, the tool has fixtures, and no test uses the legacy facade.
- Typed request and middleware have a decision record; no unapproved API break is shipped.
- No publish and no commit are performed unless requested.

## 8. Out of scope and open decisions

- Removing deprecated `have*` before 5.0.
- “One address = one schema” and `fireConfirmed`/ack.
- Broker-side request cancellation (the caller-side future is cancelled; the broker request
  completes or times out).
- Whether the migration tool should auto-rewrite `paths:` with a prefix or only report them; the
  recommended default is report-only.
- Whether typed responses are additive (`request<T, R>`) or require a new key type; decide after
  the inference prototype.
- Whether middleware is a 4.2 additive API or a 5.0 feature; decide with API-02.
